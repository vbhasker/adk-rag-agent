Chapters 1–5 built a strong retrieval engine for the query it's given. Real queries look like this:

Follow-ups

"How much does the Stratus weigh?" … "and the cargo one?" The second message alone retrieves nothing useful.

Multi-part

"Can my kid ride on the back, and is that legal in the EU?" This needs two different docs, but one query vector can only point one way.

Vocabulary gap

"can my kid ride on the back" vs the doc's "two child seats on the rear deck". Measured: the literal query never retrieves the cargo bike; "child seat on the rear deck" puts it at #1.

Orphan chunks

Part A · Transform the query

TechniqueWhat it doesUse when
RewriteChat history + follow-up → one standalone queryEvery conversational app. Non-negotiable.
Multi-query2–4 differently-worded variants, each searched, fused with RRF (Chapter 4's multi-list superpower)Vague or casual queries; vocabulary gaps
DecompositionSplit into sub-questions, one search eachMulti-part and comparison questions
HyDELLM writes a hypothetical answer; embed that (as a document) and searchShort or keyword-poor questions. Answers look like answers.
Step-backAlso search a more general version ("EU e-bike rules" for a specific case)Questions that need background principles
Coach says: the agent already does thisIn a tool-calling ADK agent, Gemini writes the search query. Rewriting comes free. So in this chapter the tool takes queries: list[str], and the docstring asks for "one query per part, plus variants". Multi-query and decomposition then happen inside the same LLM call that decides to search: no extra latency, no extra cost. Standalone transforms (query_transform.py) are for pipelines without an agent, and for the playground.

Part B · Enrich the chunks

Contextual retrieval

Before indexing, prepend context to every chunk so it can be found by what it's about, not just what it says. Three modes in Chunk.text_for_embedding(mode):

ModeIndexed textCost
nonebare chunkfree
headerNimbus Warranty Policy > What is not covered + chunkfree, deterministic
llmheader + 1–2 Gemini-written sentences situating the chunk ("This section of the Nimbus warranty lists exclusions such as…") + chunkone LLM call per chunk, once, cached (python contextualize.py)

Measured here with the local embedder: for "what is not covered by the warranty", none doesn't return warranty#2 (the exclusions) in the top 4 at all; header ranks it #2. LLM context goes further for chunks whose heading is vague ("Introduction", "Step 3").

Parent-document retrieval (small-to-big)

Index small children (~30-word sentence packs: 115 of them here) for sharp matching, but hand the LLM the parent section they belong to. Search "how do I clear stored codes" and the child "Hold the power button and the minus button together for 5 seconds…" matches, and the agent gets the whole "Resetting the display" section.

2026 best practices

  • Always rewrite follow-ups into standalone queries. With an agent, make the tool docstring demand it.
  • Let the agent emit several queries in one tool call instead of adding separate LLM calls for multi-query.
  • Contextual chunk headers are free. Do them everywhere. LLM-generated context is worth its one-time cost for important corpora; use Gemini context caching when chunking long documents.
  • Rerank against the original question, not the variants. Variants widen recall; the user's intent decides precision.
  • Budget your latency: every LLM call in the retrieval path adds hundreds of ms. HyDE and standalone multi-query are optional extras; measure them (Chapter 7) before shipping.
  • Small-to-big (or "sentence-window") retrieval is a cheap win when sections are long but answers are one sentence.
PitfallsRewriting that "fixes" error codes (E-07 → "E07 error") or product names; HyDE hallucinations leaking into the answer (only search with it, never show it); too many variants flooding RRF with noise; re-running contextualisation on every ingest (cache it).

The new problem this chapter creates

We now have a lot of knobs: chunk size, context mode, hybrid fusion, candidate depth, reranker, threshold, MMR λ, multi-query, HyDE, parent docs. Every "Try this" so far was one query and one eyeball. Is HyDE actually helping on average? Does contextual retrieval beat headers on our data? Right now we're guessing.
