Where we left off

Chapter 2 gave each whole document one vector, a blurry average of everything it talks about. Real documents are also way longer than an embedding model can read. The fix: chunk documents into focused passages, embed each chunk, and retrieve just the passages that matter. Those passages become the context for the LLM.

The two halves of every RAG system

Chunking: the most underrated decision in RAG

Too small (e.g. 1 sentence)

Precise matches, but "It lasts 800 cycles" loses what it is. The LLM gets fragments without context.

Too big (e.g. whole doc)

Blurry vectors (Chapter 2's problem), more tokens per answer, and the one relevant sentence drowns in noise ("lost in the middle").

Three strategies in chunking.py

StrategyHowOn our corpus
fixedEvery N words, sliding with overlapCuts mid-sentence and mid-list. Simple baseline.
sentencePack whole sentences up to N words; overlap by one sentenceReadable chunks, but ignores sections, so a chunk can mix "coverage" and "exclusions".
markdown (default)Split on ## headings first, keep the heading path as metadata, only split oversized sections further (paragraphs → sentences)Each chunk = one topic. 53 chunks, avg 45 words.
Coach saysLook at Chunk.text_for_embedding(). We embed "Nimbus Warranty Policy > What is not covered" + the chunk text, not the bare text. A tiny trick with a big payoff: a chunk that just says "Damage from crashes…" now knows it's about the warranty. Chapter 6 takes this idea much further (contextual retrieval).

Overlap repeats the tail of one chunk at the head of the next, so a fact that straddles a boundary survives in at least one chunk. 10–20% of the chunk size is a common start.

The vector store

A vector store holds, for every chunk: the vector, the text (so you can give it to the LLM) and metadata (source id, title, section, category…). Ours (vector_store.py) is a NumPy matrix plus a JSON file, about 60 lines long:

scores = matrix @ query_vector            # one dot product per chunk (vectors are normalised)
scores[~category_mask] = -inf             # metadata pre-filter
top = argpartition(-scores, k)[:k]        # O(n) top-k, then sort just those k

Exact search (ours)

Compares against every vector. Perfect recall, fine up to ~100k vectors on a laptop.

Approximate (ANN)

HNSW graphs, IVF clusters, Google's ScaNN: ~95–99% recall at a tiny fraction of the cost. What you get in pgvector/AlloyDB, Vertex AI Vector Search, Qdrant, Weaviate, Milvus…

Metadata filters

Pre-filter (filter, then rank, as we do) always returns k results. Post-filter (rank, then drop) can return fewer. Ask your vector DB which one it does.

Index fingerprint

The saved index stores a hash of the embedder name + every chunk. Change a doc, the chunk size or the model, and it rebuilds automatically. No stale vectors.

RAG as an ADK agent

You know ADK already, so here's the key design choice: retrieval is a tool. The agent decides when to search, can search twice with different words, and can filter by category. The whole agent is ~20 lines:

def search_knowledge_base(query: str, category: str = "") -> dict:
    """Search the Nimbus Bikes knowledge base (...)"""       # ← the docstring IS the tool description
    return {"query": query, "results": retrieve(query, top_k=4, category=category or None)}

root_agent = Agent(
    name="nimbus_support_agent",
    model=os.getenv("GEMINI_MODEL", "gemini-2.5-flash"),
    instruction=INSTRUCTION,          # search first · answer ONLY from results · cite [source_id] · admit gaps
    tools=[search_knowledge_base],
)

Grounding rules in the instruction

  • Always search before answering
  • Use only retrieved text
  • Cite [warranty#2] for every fact
  • Say "I don't know" when retrieval comes back empty

Tool vs. always-retrieve

A fixed pipeline (always retrieve, then generate) is cheaper and more predictable. Tool-based lets the model skip retrieval for "hi!" and retry with better queries. Chapter 8 goes fully agentic.

2026 best practices

  • Start structure-aware (headings, paragraphs, table rows) at ~200–500 tokens with 10–20% overlap, then measure (Chapter 7) before tuning. There is no universal best size.
  • Keep rich metadata on every chunk: source, section path, dates, product, access level. You'll need it for filters, citations and permissions.
  • Parse well before you chunk. PDFs, tables and slides need a real parser (Document AI, Gemini's native PDF understanding, or layout-aware parsers). Garbage in, garbage retrieved.
  • Other chunkers worth knowing: semantic chunking (split where embedding similarity drops), late chunking (embed the whole doc with a long-context model, then pool per chunk), and parent/child chunks (Chapter 6).
  • Long context didn't kill RAG. Gemini can read a million tokens, but retrieval is still cheaper, faster, easier to cite and permission-aware. Common 2026 pattern: retrieve generously, then let a long-context model read more.
  • Managed options on Google Cloud: Vertex AI RAG Engine (ingestion + chunking + retrieval as a service), Vertex AI Search, Vertex AI Vector Search, AlloyDB/Cloud SQL with pgvector.
PitfallsChunking tables row-by-row without the header; losing the heading context; embedding with one model and querying with another; letting the agent answer without calling the tool (fix it in the instruction, or force retrieval in a pipeline).

The new problem this chapter creates

Pure vector search is now doing all the retrieval, and Chapter 1 already showed its weak spot: exact codes, model numbers and rare terms like UN3480 or E-12. Meanwhile BM25 is sitting on the bench, great at exactly that.
