Lexical (BM25) wins on…

  • Codes & IDs: E-12, UN3480, 4.2.1
  • Names, SKUs, acronyms, rare jargon
  • New words the embedding model never saw

Semantic (vectors) wins on…

  • Paraphrases: "send it back" → returns
  • Symptoms → causes: "won't turn on"
  • Typos, other languages, vague questions

How hybrid search works

Both retrievers index the same chunks (Chapter 3's), so their results can be merged by chunk id. The only question is how to merge two lists whose scores live on different planets: BM25 gives 3.70, cosine gives 0.54.

Reciprocal Rank Fusion (RRF)

RRF(chunk) = Σlists 1 / (k + rank) with k = 60

Ignore the scores and use only the ranks. Being #1 in a list is worth 1/61, #2 is 1/62, and so on. Showing up in both lists adds the two together. Worked example from our data, query UN3480:

ChunkBM25 rankVector rankRRF scoreFinal
returns-shipping#2 (the answer)#1 → 1/61 = 0.0164#7 → 1/67 = 0.01490.0313#1 ✓
error-codes#1–#1 → 1/61 = 0.01640.0164#2
error-codes#2–#2 → 1/62 = 0.01610.0161#3

Why k = 60?

It flattens the curve so that #1 isn't wildly more valuable than #5, which makes agreement between lists matter more than a single strong vote. It comes from the original 2009 RRF paper and works well almost everywhere. Try k = 1 in the playground to see a spiky version.

Why it's the default

No score normalisation, no weights to tune, robust to a retriever having a bad day, and it fuses any number of lists (Chapter 6 fuses one list per rewritten query).

Weighted fusion (the tunable alternative)

score = α · minmax(vector) + (1 − α) · minmax(bm25)

Rescale each list's scores to 0–1, then blend. α = 1 is pure vector, α = 0 pure BM25. It can beat RRF, if you tune α on a labelled set (Chapter 7). The catch: min-max is sensitive to outliers, and one list's "best" is always 1.0 even when it's terrible.

Coach saysStart with RRF. Switch to weighted only when you have an eval set proving it's better for your data. On our 12-query scoreboard, RRF has MRR 0.917 vs weighted (α=0.5) 0.861.

2026 best practices

  • Hybrid by default. For almost any real corpus (product docs, tickets, code, legal), lexical + semantic beats either alone. The cost is one extra, cheap query.
  • Use native hybrid where you can: Vertex AI Vector Search (dense + sparse vectors in one index), Vertex AI Search, Elasticsearch/OpenSearch, Weaviate, Qdrant, Milvus, or Postgres (pgvector + full-text/BM25 extension) all do fusion server-side.
  • Retrieve deep, then cut: fuse the top 20–50 from each list, pass the top 20 on to a reranker (Chapter 5), and give the LLM the top 5.
  • Learned sparse (SPLADE-style) can replace BM25 as the lexical side: exact matching plus learned expansion.
  • Tune with data, not vibes: k, α and candidate depth are hyperparameters, and Chapter 7 gives you the harness.
PitfallsBM25 and vectors indexing different text (then ids don't line up); fusing raw scores without normalising; tiny candidate depth (a chunk at vector #25 never gets a chance); applying metadata filters to one retriever but not the other.

The new problem this chapter creates

Hybrid search is great at recall: the right chunk is almost always somewhere in the top 5–10. But the order is decided by cheap signals (word overlap, vector angle), so the best chunk isn't always #1, and LLMs pay most attention to what comes first.
