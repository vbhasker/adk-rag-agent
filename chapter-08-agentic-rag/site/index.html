Where we left off

Chapter 7 showed the hard cases: multi-part questions that need two documents, comparisons ("battery warranty vs lifespan"), and questions whose honest answer is "not in the docs" (the Nimbus Trail's price). A single search-then-answer turn can't plan, can't check its own work, and can't go back for more.

The RAG spectrum

StyleHowCost / latencyBest for
Pipeline RAGAlways retrieve → stuff prompt → answer1 LLM callFAQ bots, high volume, predictable questions
Tool RAG (Ch 3–6)LLM decides when and what to search, may retry2–3 LLM callsMost assistants. The sweet spot.
Agentic RAG (Ch 8)Plan → multi-tool research → write → verify → revise4–8 LLM callsMulti-hop, comparisons, high-stakes answers
Coach saysAgentic isn't automatically better. It's slower and pricier. Use Chapter 7's eval to prove it earns its keep on your questions. Many production systems route: simple questions go to tool RAG, hard ones go to the agent team.

The architecture: a research team in ~120 lines

State is the message bus

Each agent writes its result to session state via output_key. The next agent reads it through instruction templating: {research_notes}, {draft_answer}, and {review_feedback?} (the ? = optional, empty on round one).

Separation of duties

The researcher never answers, the writer never searches, the checker never rewrites. Narrow jobs make each prompt simpler, each failure easier to spot in the trace, and each role swappable (e.g. a cheaper model for the writer).

Explicit GAPS

The researcher must list what it couldn't find. That turns "not in the docs" from a hallucination risk into a first-class output the writer must mention.

Bounded loops

max_iterations caps cost. The checker ends the loop early by calling ADK's built-in exit_loop tool, which sets escalate=True.

root_agent = SequentialAgent(
    name="agentic_rag",
    sub_agents=[
        researcher,                                  # tools=[search_knowledge_base, get_document, list_documents]
        LoopAgent(name="write_and_check",
                  sub_agents=[writer, fact_checker],  # fact_checker: tools=[exit_loop]
                  max_iterations=3),
    ],
)

The 2026 RAG landscape: what else is out there

    

      
Managed RAG on Google Cloud
Vertex AI RAG Engine (managed ingestion, chunking, embeddings, retrieval; ADK ships a VertexAiRagRetrieval tool), Vertex AI Search (VertexAiSearchTool), Vertex AI Vector Search, AlloyDB/Cloud SQL + pgvector. Build it yourself to learn (you just did), then buy what you don't need to own.

      
GraphRAG & knowledge graphs
Extract entities and relations into a graph, then retrieve by traversal and community summaries. Wins on "connect the dots" and global questions ("what are the main themes across all tickets?"). Expensive to build; use it where relationships are the point.

      
Late interaction & multimodal
ColBERT-style token-level matching (a middle ground between bi- and cross-encoders), and ColPali-style retrieval over page images, plus Gemini's native PDF/image understanding. Tables, charts and scanned docs no longer need a lossy text parse.

      
Long context + caching
Million-token windows plus context caching make "retrieve generously, let the model read a lot" viable. Retrieval still decides what goes in, and still wins on cost, latency, freshness and permissions.

      
Retrieval over MCP & A2A
Expose your retriever as an MCP server so any agent (ADK's McpToolset, IDEs, other frameworks) can use it; let specialist agents talk over A2A. Retrieval becomes a shared service, not a copy-pasted function.

      
Security & governance
Retrieved text is untrusted input: documents can contain prompt injections. Enforce ACLs inside retrieval (filter by user permissions), redact PII at ingestion, and never let retrieved text trigger privileged tools unchecked.

      
Memory
Long-term memory is RAG over the user's own history (ADK's MemoryService + load_memory tool, Vertex AI Memory Bank). Same retrieval ideas, different corpus.

      
Ship & observe
Deploy with adk deploy to Agent Engine or Cloud Run; trace every tool call (OpenTelemetry → Cloud Trace); cache frequent questions (semantic caching); run Chapter 7's eval in CI.

Checklist for your own project

    
    
      
  1. Write 30 golden questions first, from real users if possible, including unanswerable ones. Before any code.
    2. 
      
  2. Parse & chunk structure-aware with heading context; keep metadata (source, section, date, ACL).
    3. 
      
  3. Start with hybrid + rerank (managed: Vertex AI Search / RAG Engine; self-built: pgvector + BM25 + a cross-encoder).
    4. 
      
  4. Tool-RAG agent in ADK with a queries: list[str] search tool and a strict grounding + citation instruction.
    5. 
      
  5. Measure (Chapter 7). Only then add contextual retrieval, HyDE or an agent team, and keep each one only if the numbers improve.
    6. 
      
  6. Harden: permissions in retrieval, prompt-injection awareness, tracing, cost and latency budgets, eval in CI.
