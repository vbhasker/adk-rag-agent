Where we left off

Chapter 4's hybrid search had 100% Hit@3 on the scoreboard, but not 100% at #1. For "what happens if the motor gets too hot" the E-07 overheating chunk came third, behind a chunk about cleaning (it shares "motor"). BM25 counts words and vectors compare angles, but neither actually reads the question next to the passage.

Coach saysOrder matters more than you'd think. LLMs pay most attention to the start of the context, you pay per token for every chunk, and a chunk at #6 of 5 doesn't exist at all. Recall gets the answer into the candidates; precision gets it to the top.

Two-stage retrieval: recall first, then precision

Bi-encoders vs cross-encoders

Bi-encoder (Chapters 2–4)

Query → vector. Passage → vector (precomputed). Compare. The two texts never meet, so the model can't check whether the passage answers this question. Speed: milliseconds over millions of passages.

Cross-encoder (this chapter)

[query] [SEP] [passage] → one transformer → one relevance score. Every word of the query attends to every word of the passage, so it catches negation, "which model?", and "answers vs. merely mentions". Speed: ~20 passages in tens of ms on CPU. Great for stage 2, useless for stage 1.

Three rerankers in rerank.py

RerankerHowTrade-off
cross-encoderXenova/ms-marco-MiniLM-L-6-v2 via fastembed, local CPU. Logits → sigmoid → 0..1Free, fast, private; English-centric, trained on web search

noneKeep hybrid orderThe baseline you compare against

On Google Cloud there's also the managed Vertex AI ranking API (semantic ranker), and hosted rerankers from Cohere, Voyage, Jina and others. Same idea, bigger models.

Diversity with MMR

MMR = argmaxd [ λ · relevance(d) − (1 − λ) · maxs∈selected sim(d, s) ]

Pick greedily: each next result must be relevant and different from what's already picked. Ask about "warranty" and plain top-5 returns five warranty paragraphs that overlap. MMR with λ = 0.5 swaps one of them for something new. Use it for broad or multi-part questions and whenever your corpus has near-duplicates (versions of the same doc, FAQ copies).

Relevance thresholds: permission to say "I don't know"

Cosine scores are uncalibrated (bike vs banana = 0.60, remember?). Cross-encoder scores after a sigmoid are much more meaningful, so a threshold like 0.2 can drop junk. For "Do you sell scooters?" the agent then receives nothing and the grounding instruction makes it admit that, instead of improvising from a vaguely related chunk. Set RERANK_MIN_SCORE in .env.

Metadata filters, done carefully

The agent can pass category to the tool. Filters are the cheapest precision boost there is (and essential for permissions: never retrieve what the user may not see), but a wrong filter silently hides the answer. The tool docstring now describes each category and says "only when you are sure".

2026 best practices

  • Always rerank when quality matters. It's usually the single biggest precision win after hybrid search, for a few dozen milliseconds.
  • Retrieve 20–50, rerank, keep 3–8. Tune both numbers with Chapter 7's eval.
  • Rerank the same text the LLM will see (we include the title > section header).
  • Thresholds need calibration: pick them from eval data, per reranker model.
  • LLM rerankers are great for hard, domain-specific relevance, and you can fine-tune or instruct them ("prefer official policy over forum posts"). Watch latency.
  • Filters are for permissions first, precision second. Apply access control inside retrieval, never after generation.
PitfallsReranking only the top 5 (nothing left to reorder); comparing cosine and reranker scores as if they were the same scale; an LLM-chosen filter that's wrong 10% of the time, silently; MMR on tiny candidate sets.

The new problem this chapter creates

Our retrieval stack is now strong for the query it's given. But users write terrible queries: "it's broken", "what about the other one?", "can my 8-year-old ride on the back and is that legal in Germany?" (two questions in one). No reranker can fix a query that asks for the wrong thing.
