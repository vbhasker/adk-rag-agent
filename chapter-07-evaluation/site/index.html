Where we left off

Every "Try this" so far was: one query, eyeball the result, nod wisely. That's how RAG projects end up with HyDE, three rerankers and a 400 ms latency budget that nobody can justify. From here on, every change gets a number.

Step 1 · The golden dataset

eval/golden.jsonl has 24 questions. Each has the docs that contain the answer (for retrieval metrics) and a reference answer (for answer metrics):

{"id": "q09", "type": "semantic", "question": "Is a speed chip covered by the warranty?",
 "relevant_docs": ["warranty"],
 "reference": "No. Damage from unauthorised motor tuning such as speed chips ... is not covered."}

Mix the question types

  • 6 keyword (codes, prices, versions)
  • 12 semantic (paraphrases, symptoms)
  • 3 multi-part (need 2 docs)
  • 3 unanswerable (the right answer is "I don't know")

Where real golden sets come from

  • Real user questions from logs (best)
  • Subject-matter experts
  • LLM-generated from your docs, then human-reviewed
  • Every production bug becomes a new test case
Coach saysAim for 50–200 questions for real decisions. With our 21 answerable ones, a single question moves Hit@3 by 4.8 points, so treat small differences as noise. Tiny eval sets have the confidence of a toddler with a crayon.

Step 2 · Retrieval metrics

We map retrieved chunks to their documents (first occurrence wins), so different chunking setups compare fairly. Then, for top-k:

MetricFormulaQuestion it answers
Hit@k1 if any relevant doc in top kDid we find anything useful?
Recall@krelevant found in top k ÷ all relevantDid we find everything? (multi-part questions!)
Precision@krelevant in top k ÷ kHow much noise did we send the LLM?
MRR1 ÷ rank of first relevantHow high was the first hit?
nDCG@kΣ rel/log₂(rank+1) ÷ idealWere all relevant docs near the top?

Measured with the local bge-small embedder and no reranker available, k = 3, 21 answerable questions:

  • Hybrid RRF has the best Hit@3 and Recall@3: it never misses completely, and it gets both docs for multi-part questions more often.
  • Pure vector has the best MRR here. On a tiny, clean, well-written corpus, embeddings rank the #1 hit very well. Your messy real-world corpus may disagree, and that's the point of measuring.
  • Chunk context (heading) helps: MRR 0.897 → 0.921 with the same pipeline.
  • Differences of 0.01–0.02 are one question. Don't ship based on noise.
  • Your numbers will differ with Gemini embeddings or a working cross-encoder. Run it and compare.

Step 4 · Answer metrics: the RAG triad (+2)

Context relevance / recall

Did retrieval bring the right material? (Step 3 measures this offline; eval_answers.py checks the agent's actual tool results.)

Faithfulness (groundedness)

Is every claim supported by the retrieved text? A correct fact that wasn't in the context still counts as a hallucination: the model got lucky.

Answer correctness / relevance

Does it agree with the reference and actually address the question?

Refusal accuracy

Says "I don't know" for unanswerable questions (the Nimbus Trail's price isn't in the docs!), but not for answerable ones.

Citation validity

Every [warranty#2] cited must be a chunk the agent really retrieved. Checked with a regex, no LLM needed.

Cost & latency

Tool calls and seconds per answer. Quality that times out isn't quality.

LLM-as-judge, responsibly

  • Structured output (Judgement Pydantic model), temperature 0, and a rubric in the prompt (JUDGE_PROMPT in eval_answers.py).
  • Use a strong judge model, and check the judge against ~30 human labels before trusting it.
  • Judges have biases (they favour long answers and their own style). Prefer pairwise A/B comparisons when choosing between two systems.

2026 best practices

  • Evaluate retrieval and generation separately. When an answer is wrong, you need to know which half broke.
  • Put the eval in CI. A prompt tweak, a model upgrade or a new embedding model can silently drop quality. Gate merges on the golden set.
  • Include unanswerable and adversarial questions. "I don't know" is a feature.
  • Track cost and latency next to quality, per configuration.
  • Close the loop online: log real questions and thumbs-down, trace every tool call, and promote failures into the golden set.
PitfallsEvaluating on questions you wrote while looking at the chunks (too easy); trusting an unvalidated LLM judge; changing three knobs at once; celebrating a 0.01 gain on 20 questions.

The new problem this chapter creates

Our eval shows the remaining failures are the hard ones: multi-part questions that need two documents, comparisons, and knowing when to stop and say "not in the docs". A single search-then-answer turn can't plan, check its own work or retry.
